# ADR-006 migration history append-only

## 背景

過去のマイグレーションが未導入であることをリポジトリの差分だけでは証明できないため、既存履歴の
編集可否をレビュアーの判断へ委ねると、環境ごとに適用履歴が分岐します。

Drizzle v1ではマイグレーションv3のディレクトリ形式が必要です。旧形式へ
`drizzle-kit up`を直接実行すると、既存のSQL、スナップショット、ジャーナルが削除または改名され、
追記専用の履歴を維持できません。また、Drizzle v1の標準マイグレーターは既存の
`__drizzle_migrations`を拡張し、v3のディレクトリ名を`name`へ既存データ補完します。

## 決定

### 旧形式を不変の証拠として保持する

`packages/db/drizzle/**`は、`main`に存在した31件の旧形式履歴を保存する読み取り専用の証拠です。
SQL、スナップショット、`meta/_journal.json`をバイト単位で維持し、追加、変更、削除、改名を
すべて拒否します。ランタイム、テスト、設定、運用コマンドからこのディレクトリを読みません。

旧形式の変換は、追跡対象外の一時ディレクトリへ旧履歴を複製し、固定したDrizzle Kitで公式の
`drizzle-kit up`を実行します。生成された31件のv3履歴だけを新しい正本へ追加し、旧履歴へ変換を
直接実行しません。

### v3を追記専用の正本にする

実行対象の履歴は
`packages/db/drizzle-v3/<YYYYMMDDHHmmss>_<tag>/{migration.sql,snapshot.json}`です。
変換元31件は旧ジャーナルの時刻と意味名、SQL本文、`--> statement-breakpoint`に1対1で対応させます。
既存のv3ディレクトリはSQLとスナップショットを一体として不変にし、新しい完全なディレクトリの
追加だけを許可します。既存スキーマの修正やデータ移行は、新しいv3マイグレーションで行います。

### 標準マイグレーターで台帳を更新する

旧形式を適用済みのデータベースは、Drizzle v1の標準マイグレーターで更新します。既存の
`__drizzle_migrations`の`id`、`hash`、`created_at`を保持したまま、標準の更新処理が`name`と
`applied_at`を追加し、変換後のディレクトリ名を`name`へ既存データ補完します。旧行の`applied_at`は
`NULL`のままです。変換済みの名前を適用済みと判定することで、既存DDLを再実行しません。

独自のマイグレーション読み込み処理、旧形式とv3の二重実行、別の台帳、ジャーナルへの代替経路は
追加しません。台帳行がローカル履歴へ一意に対応しない場合は、推測で対応付けず失敗させます。

## 理由

旧履歴を証拠として固定し、実行対象をv3へ一度だけ切り替えることで、全環境で同じ履歴を再現し、
適用済みデータベースとの分岐を防ぎます。Drizzleの標準変換と標準マイグレーターへ委譲することで、
リポジトリ固有の互換処理と追加の保守対象を持ちません。

## 検討した代替案

- 未導入の証拠があれば既存履歴を編集する: 証拠の情報源と承認条件が複雑になる
- 旧ディレクトリへ`drizzle-kit up`を直接実行する: 追跡済み履歴を削除、改名する
- 旧形式とv3を並行して実行する: 実行順序と台帳の正本が2つになる
- マイグレーションをまとめ直す: 現在有効な本番データベースとの整合が難しい

## 結果

修復用マイグレーションが増える場合があります。v3のディレクトリ名は時刻と読みやすい意味名を
持ちます。旧履歴は実行時に不要でも、追記専用であったことを検証する証拠として残ります。

Drizzle v1を初めて適用する前は変更全体を戻せます。標準マイグレーターが台帳へ列を追加した後は、
旧ランタイムへ戻す場合も追加列を削除しません。新しいv3マイグレーションを適用した後は旧形式へ
戻さず、追加のv3マイグレーションで前方修正します。本番への導入、遠隔データベースの変更、
バックアップと照合は別の明示承認を必要とします。

## 強制方法

- `origin/main`と比較し、`packages/db/drizzle/**`の全差分を拒否する
- 既存の`packages/db/drizzle-v3/**`の変更、削除、改名を拒否する
- `migration.sql`と`snapshot.json`を持つ新しいv3ディレクトリの追加だけを許可する
- 旧31件と変換後31件の時刻、意味名、SQL本文、`--> statement-breakpoint`を照合する
- ランタイム、テスト、設定、運用コマンドから旧履歴への参照がないことを検査する

## 検証

- 履歴の静的検査
- 新規データベースと各意味的な途中状態からの更新テスト
- v1台帳更新後の`id`、`hash`、`created_at`保持、`name`補完、DDL非再実行の検査
- 現在のスキーマとv3履歴の不整合検査
